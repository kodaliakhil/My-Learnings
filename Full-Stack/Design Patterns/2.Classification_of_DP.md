# Classification of Design Patterns


Design patterns are reusable ways to solve common design problems in software. They differ in their complexity, level of detail, and scale of applicability. Some patterns solve small, language-specific problems, while others help shape the architecture of an entire application.


A useful way to understand this is through the analogy of road construction. To make an intersection safer, you might install traffic lights. That is a smaller, local solution. But if the problem is larger, you might build a multi-level interchange with underground passages for pedestrians. That is a bigger, system-level solution.


Design patterns work in a similar way. Some are small and specific. Others are large and broad.


---


## Patterns by Scale


Design patterns can first be classified by their scale. The two important levels mentioned here are:


1. Idioms

2. Architectural patterns


---


## Idioms


Idioms are the most basic and low-level patterns.


They usually apply to only one programming language. Because of this, they are closely tied to the way a specific language works. An idiom may be useful in one language but may not apply in another.


In simple words:


> Idioms are small, language-specific patterns.


They are useful when solving local design problems at the code level.


---


## Architectural Patterns


Architectural patterns are the most universal and high-level patterns.


Unlike idioms, architectural patterns can be implemented in virtually any programming language. They are not limited to a single language. They are used to design the architecture of an entire application.


In simple words:


> Architectural patterns are broad patterns used to design whole applications.


They work at a much larger scale than idioms.


---


## Patterns by Intent


Apart from scale, design patterns can also be classified by their intent, or purpose.


This classification answers a simple question:


> What problem is this pattern trying to solve?


Based on intent, the patterns are grouped into three main categories:


1. Creational patterns

2. Structural patterns

3. Behavioural patterns


Each group has a different purpose in software design.


---


# Creational Patterns


Creational patterns focus on object creation.


Their main purpose is to provide object creation mechanisms that increase flexibility and reuse of existing code. Instead of creating objects in a rigid way, creational patterns help make the creation process more flexible.


In simple words:


> Creational patterns are about how objects are created.


The creational patterns covered here are:


- Factory Method

- Abstract Factory

- Builder

- Prototype

- Singleton


---


## Factory Method


The Factory Method pattern provides an interface for creating objects in a superclass.


However, it allows subclasses to alter the type of objects that will be created.


In simple words:


> Factory Method lets subclasses decide which type of object to create.


---


## Abstract Factory


The Abstract Factory pattern lets you produce families of related objects without specifying their concrete classes.


This is useful when the code needs to work with related objects but should not depend on their exact classes.


In simple words:


> Abstract Factory creates related objects without naming their exact classes.


---


## Builder


The Builder pattern lets you construct complex objects step by step.


It allows you to produce different types and representations of an object using the same construction code.


In simple words:


> Builder helps create complex objects one step at a time.


---


## Prototype


The Prototype pattern lets you copy existing objects without making your code dependent on their classes.


Instead of creating a new object from scratch, this pattern allows you to copy an existing one.


In simple words:


> Prototype creates new objects by copying existing objects.


---


## Singleton


The Singleton pattern ensures that a class has only one instance.


It also provides a global access point to that instance.


In simple words:


> Singleton makes sure there is only one instance of a class.


---


# Structural Patterns


Structural patterns explain how to assemble objects and classes into larger structures.


Their goal is to keep these structures flexible and efficient. They help organise relationships between objects and classes.


In simple words:


> Structural patterns are about how objects and classes are assembled.


The structural patterns covered here are:


- Adapter

- Bridge

- Composite

- Decorator

- Facade

- Flyweight

- Proxy


---


## Adapter


The Adapter pattern allows objects with incompatible interfaces to collaborate.


In simple words:


> Adapter helps incompatible objects work together.


---


## Bridge


The Bridge pattern lets you split a large class or a set of closely related classes into two separate hierarchies:


1. Abstraction

2. Implementation


These two hierarchies can then be developed independently of each other.


In simple words:


> Bridge separates abstraction from implementation.


---


## Composite


The Composite pattern lets you compose objects into tree structures.


It then allows you to work with these structures as if they were individual objects.


In simple words:


> Composite lets you treat a group of objects like a single object.


---


## Decorator


The Decorator pattern lets you attach new behaviours to objects.


It does this by placing those objects inside special wrapper objects that contain the behaviours.


In simple words:


> Decorator adds behaviour by wrapping an object.


---


## Facade


The Facade pattern provides a simplified interface to a library, a framework, or any other complex set of classes.


In simple words:


> Facade hides complexity behind a simple interface.


---


## Flyweight


The Flyweight pattern helps fit more objects into the available amount of RAM.


It does this by sharing common parts of state between multiple objects instead of keeping all the data in each object.


In simple words:


> Flyweight saves memory by sharing common data.


---


## Proxy


The Proxy pattern provides a substitute or placeholder for another object.


A proxy controls access to the original object. It can perform something either before or after the request reaches the original object.


In simple words:


> Proxy controls access to another object.


---


# Behavioural Patterns


Behavioural patterns focus on effective communication and the assignment of responsibilities between objects.


They help objects interact with each other in a clean and organised way.


In simple words:


> Behavioural patterns are about how objects communicate and share responsibilities.


The behavioural patterns covered here are:


- Chain of Responsibility

- Command

- Iterator

- Mediator

- Memento

- Observer

- State

- Strategy

- Template Method

- Visitor


---


## Chain of Responsibility


The Chain of Responsibility pattern lets you pass requests along a chain of handlers.


When a handler receives a request, it decides either to process the request or pass it to the next handler in the chain.


In simple words:


> Chain of Responsibility passes a request through a chain until it is handled.


---


## Command


The Command pattern turns a request into a stand-alone object.


This object contains all information about the request. This makes it possible to pass requests as method arguments, delay or queue their execution, and support undoable operations.


In simple words:


> Command converts a request into an object.


---


## Iterator


The Iterator pattern lets you traverse elements of a collection without exposing its underlying representation.


The collection could be a list, stack, tree, or another structure.


In simple words:


> Iterator lets you go through a collection without knowing how it is built inside.


---


## Mediator


The Mediator pattern reduces chaotic dependencies between objects.


It restricts direct communication between objects and forces them to collaborate only through a mediator object.


In simple words:


> Mediator makes objects communicate through one central object.


---


## Memento


The Memento pattern lets you save and restore the previous state of an object.


It does this without revealing the details of the object's implementation.


In simple words:


> Memento saves and restores object state safely.


---


## Observer


The Observer pattern defines a subscription mechanism.


This mechanism notifies multiple objects about events that happen to the object they are observing.


In simple words:


> Observer notifies interested objects when something changes.


---


## State


The State pattern lets an object alter its behaviour when its internal state changes.


It appears as if the object changed its class.


In simple words:


> State changes an object's behaviour based on its current state.


---


## Strategy


The Strategy pattern lets you define a family of algorithms.


Each algorithm is placed into a separate class, and their objects become interchangeable.


In simple words:


> Strategy lets you switch between different algorithms.


---


## Template Method


The Template Method pattern defines the skeleton of an algorithm in the superclass.


Subclasses can then override specific steps of the algorithm without changing its overall structure.


In simple words:


> Template Method defines the main algorithm structure and lets subclasses change certain steps.


---


## Visitor


The Visitor pattern lets you separate algorithms from the objects on which they operate.


In simple words:


> Visitor separates operations from the objects they work on.


---


# Quick Comparison


| Category | Main Focus | Simple Memory Hook |

|---|---|---|

| Creational Patterns | Object creation | How objects are created |

| Structural Patterns | Object and class assembly | How objects are connected |

| Behavioural Patterns | Communication and responsibility | How objects interact |


---


# Final Summary


Design patterns can be classified in two major ways.


First, they can be classified by scale. Idioms are low-level and language-specific, while architectural patterns are high-level and can shape the design of an entire application.


Second, they can be classified by intent. Creational patterns deal with object creation, structural patterns deal with assembling objects and classes, and behavioural patterns deal with communication and responsibility between objects.


The core idea is simple:


> Design patterns help developers solve design problems at different levels, from small language-specific solutions to large application-wide architecture.
